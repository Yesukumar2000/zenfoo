# Zenfoo Demo Data

Everything needed to fill an empty database with a believable Zenfoo: a real
product catalogue, vendors with KYC documents, customers with deliverable
addresses, delivery partners, and 90 days of order history.

---

## TL;DR

```bash
# 0. Point DB_* at a LOCAL database first. See "Safety" below.

php artisan zenfoo:demo-documents          # KYC / banner images (no DB access)
php artisan zenfoo:fetch-catalog --resume  # real products + photos -> JSON
php artisan db:seed --class=QuickCommerceCatalogSeeder
php artisan zenfoo:demo-world              # vendors, customers, drivers, orders, merchandising
```

Undo the last step at any time:

```bash
php artisan zenfoo:demo-world --purge
```

## Recommended path (fastest to a working demo)

1. Restore the production dump into a local database (see *Restoring the live
   dump locally*) and point `.env` at it. ~10 minutes, and you get the real
   catalogue, stores and settings for free.
2. `php artisan zenfoo:demo-documents` — instant, no network, no DB.
3. `php artisan zenfoo:demo-world` — the whole demo world.
4. Only if produce tiles are blank: `php artisan zenfoo:fetch-catalog --resume`
   then re-run `QuickCommerceCatalogSeeder`. This is the slow step (Open Food
   Facts is rate-limited to ~10 searches/minute), so leave it until last.

**Do not seed people or orders into the live database.** If you must put
something on live for the customer app to show, use `--only=merchandising`,
which only adds banners, promo codes and offers. Preview anything first with:

```bash
php artisan zenfoo:demo-world --dry-run --i-know-this-is-live
```

`--dry-run` runs every INSERT inside a transaction, prints the exact per-table
row counts it would add, then rolls back. Nothing is committed, so it is safe
to point at production — and any constraint violation surfaces there rather
than half-way through a real run.

## Safety

`.env` in this repo has `APP_ENV=local` but `DB_HOST=auth-db1754.hstgr.io` —
**that is the live Hostinger database.** `zenfoo:demo-world` detects this and
refuses to run. Override only if you genuinely mean it:

```bash
php artisan zenfoo:demo-world --i-know-this-is-live
```

Nothing pre-existing is ever modified. Every row the demo world writes is
marker-tagged so `--purge` deletes exactly its own rows:

| Table | How demo rows are identified |
|---|---|
| `sellers`, `admins`, `users` | `email LIKE '%@demo.zenfoo.test'` |
| `delivery_boys` | `remark LIKE 'ZFDEMO%'` |
| `orders` | `orders_id LIKE 'ZFDEMO%'` |
| everything else | reached through the ids above |

`.test` is a reserved TLD, so the customer marker doubles as a guarantee that
no demo address can receive real mail. (`users` has no `auth_uid` column — it
was dropped in 2024 — which is why the marker is the email domain.)

Existing `vehicles` and `store_locations` are **reused, not duplicated**: demo
drivers attach to the real Zenfoo hubs already configured for Hyderabad and
Kurnool. New ones are only created for a city that has none.

If a name or mobile collides with a real record, the seeder **skips** it rather
than overwriting.

## Where the data comes from

| Content | Source | Licence / cost |
|---|---|---|
| Packaged SKUs (name, brand, pack size, barcode, packshot) | [Open Food Facts](https://world.openfoodfacts.org) | ODbL, free, no key |
| Personal / home / baby / pet care | Open Beauty Facts, Open Products Facts | ODbL, free, no key |
| Loose produce, meat, fish photos | Wikipedia PageImages → Unsplash → Wikimedia Commons | CC / Unsplash licence |
| Prices | Derived per category from a ₹/100g base, hash-seeded | — |
| People, addresses, orders | Generated by the demo seeders | — |
| KYC / proof documents | Drawn locally by `zenfoo:demo-documents` | — |

Zepto and Blinkit are **not** scraped. Their product imagery is retailer/brand
copyright and their terms forbid it; Open Food Facts carries the same Amul,
Britannia and Parle packshots under an open licence, so there is no reason to
take the risk.

## The commands

### `zenfoo:demo-documents`

Draws 147 images into `public/images/demo-docs/`: PAN, Aadhaar-layout ID,
FSSAI licence, GST certificate, cancelled cheque, storefront, driving licence,
driver avatar.

These are **deliberately not convincing**. Every one carries a diagonal
`SAMPLE — NOT A VALID DOCUMENT` watermark, a footer stating it was
autogenerated, and numbers that fail real validation (Aadhaar masked to
`XXXX XXXX 1234`, PAN in a reserved `ZZ` series, no emblem or seal). They
exercise the document viewer, zoom modal and approve/reject flow — nothing
more. Do not replace them with real-looking forgeries.

Options: `--force` to redraw existing files.

### Product images

Packaged SKUs use the Open Food Facts packshot for that exact barcode, so the
photo always matches the product.

Loose items (vegetables, fruits, meat, fish) have no packshot, so they resolve
in this order:

1. **Wikipedia article lead image** — relevance is guaranteed by construction
   (the lead image of *Tomato* is a tomato), key-less and effectively
   unlimited. 53 of the 54 produce items resolve here.
2. **Unsplash** — prettier food photography, but the demo tier allows only
   50 requests/hour.
3. **Wikimedia Commons search** — last resort; its keyword search happily
   returns a cooked curry or a book plate.

Two filters keep step 1 honest. `WIKI_TITLE` overrides names that resolve to
the wrong subject — *Kiwi* is a bird, *Drumstick* is a drum stick,
*Ladyfinger* is a sponge biscuit, *Orange* is a disambiguation page.
`WIKI_BOTANICAL_REJECT` drops lead images that are 1887 Köhler lithographs or
photos of the living plant rather than the harvested produce (*Coriander*,
*Papaya*, *Curry tree*, *Spinach* in flower, *Drumstick* flower); those fall
through to the photo sources instead.

To backfill images without re-fetching product data:

```bash
php artisan zenfoo:fetch-catalog --resume
php artisan db:seed --class=QuickCommerceCatalogSeeder
```

### `zenfoo:fetch-catalog`

Builds `database/seeders/data/qc_catalog*.json` from the open databases above.
No DB access — the JSON is reviewable before anything is seeded.

Open Food Facts rate-limits to ~10 searches/minute, so a full run is slow by
design (`--sleep=13` between calls). Useful flags:

- `--only=17,19` — build specific stores
- `--resume` — keep categories already in the output, retry only failures
- `--skip-images` — build the data first, backfill photos later

### `zenfoo:demo-world`

Runs the four demo seeders in dependency order.

- `--only=vendors,customers,drivers,orders` — run a subset
- `--purge` — remove everything it created
- `--i-know-this-is-live` — bypass the production guard

## What gets created

| Stage | Volume | Tables |
|---|---|---|
| vendors | 12 | `admins`, `sellers`, `seller_bank_accounts` |
| customers | 150 | `users`, `user_addresses`, `wallet_transactions` |
| drivers | 25 | `admins`, `delivery_boys`, `delivery_boy_documents`, `delivery_boy_emergency_contacts`, `vehicles`, `store_locations`, `delivery_boy_store_location` |
| orders | 800 over 90 days | `orders`, `order_items`, `transactions`, `wallet_transactions`, `delivery_boy_transactions`, `product_ratings` |
| merchandising | 6 promos, 5 sliders, 3 offers, 2 campaigns | `promo_codes`, `sliders`, `zenfoo_offers`, `brand_campaigns`, `favorites`, `carts`, `customer_app_sections` |

Cities: **Hyderabad** (~72% of customers) and **Kurnool**. Addresses, vendors
and hubs are scattered inside each city's delivery radius, so distance-based
delivery charges and dispatch radius checks behave normally.

Volumes live in `database/seeders/DemoWorld/DemoWorld.php` (`N_VENDORS`,
`N_CUSTOMERS`, `N_DRIVERS`, `N_ORDERS`, `DAYS_BACK`) — edit and re-run.

### Deliberate realism

- Order volume is weighted towards recent weeks and evening slots, so the
  dashboard charts have a shape instead of a flat line.
- Status mix is 74% delivered / 9% cancelled / 3% returned, with the rest
  in-flight. Anything still moving is forced to be recent — a two-month-old
  "Shipped" order reads as a bug, not demo data.
- `orders.status` is the same `[[status_id, "d-m-Y h:i:sa"], …]` trail the
  customer API writes, with one entry per transition, so the tracking timeline
  renders properly.
- Prepaid cancellations refund to the **wallet**, matching live policy.
- Vendors and drivers span approved / pending / rejected / deactivated, so the
  admin panel's filter tabs are never empty. Two drivers are flagged
  problematic.
- ~33% of customers arrive via another customer's `friends_code`, giving the
  referral payout job real pairs to process.

### Deliberate omissions

- **Drivers are created offline** — no rows in the session tables. Online
  sessions without GPS freshness are exactly the phantom-online problem that
  soaks up undelivered orders. Bring drivers online from the app to demo
  dispatch.
- `orders_priority` is never set to `1`, which would make a driver invisible to
  seller orders and silently break a dispatch demo.

## Restoring the live dump locally

The quickest way to a realistic local database is to restore a production dump
and seed on top of it:

```bash
mysql -u root -e "CREATE DATABASE zenfoo_local CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;"
mysql -u root zenfoo_local < "u675966105_zenfoo (4).sql"
```

Then point `.env` at it (`DB_HOST=127.0.0.1`, `DB_DATABASE=zenfoo_local`,
`DB_USERNAME=root`) and run `zenfoo:demo-world`. The seeders were validated
column-by-column against that dump, including which columns are NOT NULL.

Note the restored dump contains **real customer names, mobile numbers, emails
and addresses**. Treat a local copy as production data: don't commit it, don't
point a public demo at it, and delete it when you're done.

## Merchandising

The `merchandising` stage creates the demo promo codes orders reference
(`ZFWELCOME`, `ZF50OFF`, `ZFFRESH20`, `ZFWEEKEND15`, `ZFBIGCART`, plus one
expired `ZFEXPIRED` so the expired-promo state is visible), five home-screen
sliders, three order-milestone offers, two brand campaigns built from real
products of a real brand, and favourites / abandoned carts for a slice of the
customers.

Artwork comes from `zenfoo:demo-documents` (`banner-*.png`). Those banners get
a small "ZENFOO DEMO ASSET" corner tag rather than the SAMPLE watermark — a
watermark across the home carousel would read as broken, not honest.

**Home rails** (`customer_app_sections`) are only seeded when that table is
**empty**. Live data already has curated sections and there is no marker column
to purge by, so the seeder leaves existing merchandising alone.
